10. [x] **[Agent UX]** Use `status_log.jsonl` to surface richer agent status/progress.

    _Done, plus two related status-pipeline fixes:_

    - **Stuck in "starting".** Status writes used second-resolution `RFC3339`, and the JSON poller skipped any update whose timestamp wasn't lexically `>` the last one. The spawn's `starting` write and the `SessionStart` `running` hook routinely land in the same wall-clock second, so the poller recorded `starting@T` then dropped `running@T` (`T <= T`) — and a fast agent could run its whole lifecycle inside that second, leaving it stuck in `starting` even after it finished. _Fix:_ all status timestamps are now `RFC3339Nano`, and the poller compares by parsing to `time.Time` (`statusTimeAfter`) rather than string compare (also robust to `RFC3339Nano`'s trailing-zero trimming, which breaks lexical ordering).

    - **Richer states (`waiting` vs `finished`).** `Stop`/`AfterAgent` used to always map to `waiting`, conflating "done" with "needs you". Added a `finished` status: a finished turn maps to `waiting` only when the agent ended by asking a question (trailing `?` in its last message — best-effort, agents expose no explicit "I need input" signal), otherwise `finished`. The agent also goes to `waiting` when it *invokes* a tool that blocks on the user — a `PreToolUse` for `AskUserQuestion`/`ExitPlanMode` (`isUserInputTool`), surfacing the question/plan text as the pending message — and on any `Notification` (permission prompt or the idle "waiting for your input" nudge; previously only `ToolPermission` did). `finished` keeps the session alive (vs `stopped` = session ended), so the dot stays green.

    - **Richer progress (issue #10 proper).** `internal/heads/activity.go` tails `status_log.jsonl` (last 64 KiB) in `enrichAgentStatus`, surfacing a live `activity` line for running agents (the current tool action — `$ go test`, `Editing foo.go`, `Reading bar.go`, … across Claude/Gemini/Copilot tool names) plus the most recent `last_message`. New `AgentStatusInfo.activity` API field. The web sidebar item and the agent-detail header now show a status badge + a detail line (⏳ activity while running, 💬 last message / question while waiting/finished).

[x] **[Security]** **Run artifact generator commands inside the sandbox.** Previously `internal/artifacts/artifacts.go` ran each `[[artifacts]]` command directly on the host (`exec.CommandContext("sh", "-c", spec.Command)` with `os.Environ()`) — no bwrap/sandbox-exec, unlike agents and the web shells. This was a documented #17 follow-up, but it was a real **sandbox-escape / RCE**, not just "trusted config runs on the host":

    - The *command string* is trusted (read from the daemon's live merged config in `http/artifacts.go`, **not** from the checked-out ref), so an attacker can't inject a new command via a branch's `.hydra/config.toml`.
    - But the trusted command **executes inside an attacker-controllable checkout** (`runDir` = an ephemeral worktree of a caller-supplied `BaseRef`/`HeadRef`, the agent's own branch, or the head's uncommitted working tree). Build tooling run there executes the ref's code: e.g. the home-page screenshot generator (#27) runs `bun install` (which fires `postinstall`/`preinstall` lifecycle scripts from the checkout's `package.json`) and `bun take-screenshot.ts` (the ref's own copy). So **a sandboxed agent can write a malicious `package.json` postinstall, and the moment a user opens the Artifacts panel on its diff, that code runs unsandboxed on the host with the user's credentials + network** — defeating the agent sandbox.

    _Fix:_ route the command through `sandbox.BuildSpec` like `internal/heads/heads.go` does for spawn/resume/shell — checkout dir + `HYDRA_ARTIFACT_OUTPUT` dir writable, the dev caches writable (go-build/bun/magefile, as agents get), git common dir writable for the ephemeral worktree, **network enabled** (matches the agent default; needed for cold `bun install`/`go mod download`, and warm caches keep it mostly offline anyway). Verify on host — bwrap can't run nested in-session (`sandbox-userns-blocked-in-session`).

    _Escape hatch (design decision):_ support an explicit per-script opt-out so a genuinely self-contained, audited command can run on the host. **Red flag to respect:** "trusted config" only authorizes *which command runs* — it does **not** make the *diffed ref's contents* safe, and that is where the danger is. The opt-out must therefore be sandboxed-by-default and named to signal danger (e.g. `unsafe_host = true`, not a bland `sandbox = false`), documented as "runs the diffed ref's code on the host unsandboxed — only enable for audited commands when you trust every ref you'll compare." Heavy builds (like the screenshot generator) are the scripts most tempted to set it *and* the ones running the most untrusted code, so it should not be made to look routine.

    _Lesser hardening (same pass):_ cap concurrent generations (distinct refs currently build in parallel with only a per-key dedupe lock — a mild fork-bomb/DoS vector) and consider CPU/mem/process limits in addition to the existing wall-clock timeout.

    _Fixed:_ `artifacts.generate` now routes the command through `sandbox.BuildSpec` via a new `Manager.buildCommandSpec`. By default the command runs confined (the launch `Spec` is run with `exec.CommandContext`, mirroring `session/pty_unix.go` but without a PTY): the checkout/`WorktreePath` + `HYDRA_ARTIFACT_OUTPUT` dir + dev caches (`config.ResolveSandboxOptions("")`) + git common dir are writable, credentials are masked, `HardenGUI`/`Seccomp` on, **network enabled**, and the checkout dir is added to `MISE_TRUSTED_CONFIG_PATHS` when the host trusts the project (the `miseTrustEnv`/`hostTrustsMiseConfig` helpers moved from `internal/heads` to `sandbox.MiseTrustEnv` so both reuse them). The escape hatch shipped as `config.ArtifactScript.UnsafeHost` (`unsafe_host = true`), which sets `sandbox.Options.NoSandbox` so the command runs unconfined on the host — documented in the struct as "runs the diffed ref's code on the host unsandboxed; only for audited commands when you trust every ref you'll compare," deliberately not used by the #27 screenshot generator. Concurrent generations are capped by a `maxConcurrentGen` (2) semaphore in the `Manager`, on top of the existing wall-clock timeout; CPU/mem/process rlimits were left out (bwrap has no cgroup story without root — noted, not done). Verify on host — bwrap can't run nested in-session (`sandbox-userns-blocked-in-session`); the unit tests cover the cache/error logic via `unsafe_host` and gate the real-sandbox test on `sandbox.Available()`. **To check on host:** the #27 generator runs headless Chromium (Playwright) inside the userns sandbox; it already launches with `--no-sandbox` (so Chromium won't try to nest its own userns sandbox), but the full build → boot → screenshot path under bwrap is unverified here. If something can't initialise, prefer fixing the script over setting `unsafe_host`.

[x] **[Diff viewer]** **Selecting text in the diff periodically resets the selection.** The agent terminal WS fires a `diff_refresh` event **every 20 seconds** (`internal/http/terminal.go` periodic ticker), not just when a git command is detected. Each one drove a background "silent" refresh (`externalRefreshTrigger` in `DiffViewer.tsx`) that called `setDiff(d)` with a brand-new `DiffResponse` — even when nothing had changed — so every `file` object got a new reference, `FileDiff` re-rendered, and React reconciled new content into the DOM nodes the browser's text selection was anchored to, collapsing it mid-drag. (It is _not_ the syntax-highlight `useMemo` or the 1s status `setTick` re-render: a plain re-render with identical `__html` is a no-op for React, so those preserve the selection — only replacing the diff *state* loses it.) _Fixed, two parts:_ (a) `applySilentDiff` now compares the fetched diff against the last-applied content (`JSON.stringify(d.files)`) and **no-ops when unchanged**, so the 20s idle ticker never touches the DOM (also preserves per-file context expansions); (b) when the content _has_ changed but the user has a non-collapsed selection inside the diff, applying is **deferred** — the pending diff (plus its per-file context snapshot) is held in a ref and flushed by a `selectionchange` listener once the selection clears (newest fetch wins). User-initiated refreshes (manual button, commit-selector changes) are unaffected — losing the selection there is expected.

    _Recurrence + real fix (with #35):_ the frontend-only guards above reduced but didn't eliminate the wipe, because the trigger itself kept firing. The 20s ticker still drove a silent refresh every tick, and that refresh **always** called `setCommits(c)` with a brand-new array (it was never gated like the diff was) — re-rendering `DiffViewer` on every idle tick even when the diff no-op'd. Fixed at the source by removing the blind ticker (see #35) so no `diff_refresh` is emitted while the worktree is idle, **and** gating the silent `setCommits` on a real change (compare the commit-sha list; skip `setCommits` when identical) so even a stray refresh produces zero state updates.

    _Actual root cause (found by driving the real `DiffViewer` in headless Chromium with a mocked API and probing DOM-node identity across a re-render):_ the earlier note above ("a bare re-render is a no-op for React, so it preserves the selection") was **wrong** for a partial, sub-line selection. The bug reproduces on _any_ `DiffViewer` re-render — including a bare parent re-render that changes nothing — and specifically snaps a partial selection to whole-line-or-nothing. Why: `FileDiff` is wrapped in `memo()`, but the parent passed it `onShow={() => handleShowFile(f.path)}` — a **fresh function identity on every render**. That broke the memo, so every re-render re-rendered every `FileDiff` and React re-applied the highlighted lines' `dangerouslySetInnerHTML`, recreating the inner syntax-token text nodes the selection's range is anchored to; the range's endpoints detach and it collapses. (The outer line element is _not_ recreated — confirmed by node-identity probing — only the inner token nodes, which is why a sub-line selection dies while the line itself stays put.) _Fixed:_ stabilise the `onShow` prop with a per-path callback cache (`getShowCallback`, mirroring `getFileRef`) so `FileDiff`'s `memo()` holds and a no-op re-render never touches the line DOM. With this, partial selections survive bare re-renders, silent refreshes, and repeated idle ticks (all three asserted PASS by the CDP harness; all three were FAIL before the prop was stabilised). The diff no-op guard, selection-defer, and `setCommits` gating remain as complementary reducers of needless refreshes/re-renders.

[x] **[Terminal]** **Agent terminal opens at a fixed width and never reflows on resize (the real #32 root cause).** #32 fixed the *frontend* fit/ResizeObserver plumbing, but the agent (e.g. Claude) still rendered at a fixed width forever while interactive bash shells resized fine. The frontend was exonerated by a headless-Chromium repro of the exact component CSS: `FitAddon.fit()` correctly recomputes cols on every width change and `fitAndSend` ships them to the PTY. The actual cause was in the sandbox: `internal/sandbox/linux.go` passed bwrap `--new-session` for agents (omitted only for interactive shells, to preserve job control). `--new-session` calls `setsid()`, which **drops the PTY as the controlling terminal** — and creack/pty already starts the sandbox with the slave as its ctty (`Setsid`+`Setctty`). With no controlling terminal there is no foreground process group for the kernel to signal, so the `TIOCSWINSZ` we issue on the master (`session.resize` → `pty.Setsize`) delivered **no SIGWINCH** to the agent; it kept rendering at its initial size. As agents commit, this is constant heavy disk I/O (visible in the daemon log as a stream of `worktree remove`/`worktree add` pairs). Switching an **existing** worktree with `git checkout --detach --force <sha>` only writes the files that *differ* between its current and target commit, which for successive agent commits is a handful — far cheaper than a full re-materialisation.

    _Design (max 4 slots):_
    - A per-`Manager` **slot pool** of up to **4** persistent detached worktrees under `.hydra/local/artifacts/slots/<n>`. `acquire(sha)`: (1) reuse a free slot already on that SHA with **zero git work** (affinity); else (2) reuse any free slot via incremental `checkout --detach --force`; else (3) create a new slot if under the cap; else (4) wait for one to free. `release` returns the slot for reuse. Generations are already capped at 2 concurrent (`maxConcurrentGen`), so ≤2 slots are ever held at once and the other ≤2 stay warm on recent commits for affinity hits (the common "base fixed, head moves" / "head fixed, base moves" diff patterns). The slow git work happens **off the pool lock** (reserve under lock, check out unlocked) so it never serialises other acquires/releases.

[x] **[Sandbox]** **Shared-namespace host: let a head's agent and its sandboxed bash terminals share one writable `cow_paths` overlay** — and make it the default (was the experimental `HYDRA_SHARED_NS=1` spike, now removed as a flag). overlayfs corrupts if two live overlay *mounts* share one `upperdir`, so previously every session got its own `bwrap` and bash terminals were mounted **read-only** on the head's COW upper (the `Read-only file system` error writing to a `cow_paths` dir from a sandboxed shell).     _Architecture:_ a per-head "namespace host" — one `bwrap` whose pid-1 is a small supervisor (`hydra __sandbox-init`) that spawns further PTY-attached children on demand and passes their master fds back to the daemon over a unix control socket (`SCM_RIGHTS` fd passing; bwrap has no `exec`, and joining a userns gives a *fresh* mount ns, so the only way into the existing overlay is to be spawned as a child of a process already inside).
    - `internal/nshost` (new): `Serve(socket)` supervisor (pid-1 in the bwrap), `Client.Spawn(req)` daemon side, `*Spawned` satisfying the session PTY shape (`Read`/`Write`/`Resize`/`Wait`/`Signal`/`Pid`/`Close`). Windows stub returns "unsupported".

    - `internal/session`: `Session.proc` is now an interface (`PTY`) backed by either the local `ptyProcess` or a remote `nshost.Spawned`; `Registry.Start` split into `reserve()`+`register()`; new `Registry.StartWithProc(...)` backs a session with an already-running remote PTY.
    - `internal/heads/nshost.go` (new): `ensureNamespaceHost` launches the supervisor bwrap once per head (reusing the agent's exact sandbox options + writable COW, plus the control-socket dir writable), with per-head locking so concurrent callers block on a `ready` channel instead of relaunching; a single watcher goroutine evicts the registry slot + reclaims resources on supervisor exit (crash or kill), so the next attach/resume re-creates a fresh host; `removeNamespaceHost` tears it down synchronously. `startAgentSession` runs the agent as the supervisor's first child; `StartShellSession` spawns sandboxed bash as a sibling child; `runPreExitInNamespace` runs `pre_exit_script` in the still-live supervisor before teardown (bounded by `preExitTimeout`, killed via the supervisor since the master fd is blocking). `internal/sandbox` `WrapPreSpawn` runs `pre_spawn_script` inside the supervisor's bwrap too. Kill order: agent session → bash shells → pre-exit hook → tear down supervisor → remove worktree/branch.

    _Now the default (this change):_ removed `sharedNSEnabled()` / the `HYDRA_SHARED_NS` env gate and the standalone "one bwrap per agent session" branch in `startAgentSession` — the agent always launches through the namespace host. `StartShellSession` (sandboxed) and `pre_exit` keep their **runtime** fall-through to a standalone sandbox for the rare case where no supervisor is live (e.g. before the agent's first spawn, or after a host crash): a sandboxed shell then still gets read-only COW, which is correct since there's no writable-overlay owner to share with.     _Design properties (not bugs):_ one policy per namespace (everyone shares the head's seccomp/network/masks/writable paths — intended: a shared terminal has the same confinement as the agent); sandboxed bash terminals still skip `pre_spawn_script` (an agent-launch hook, not a per-shell one). bwrap installs its own pid-1 reaper (we don't pass `--as-pid-1`), so orphaned grandchildren are collected there rather than accumulating as zombies.

    _Proven vs. needs a host:_ the spawn/fd-passing/exit machinery is proven end-to-end **without** bwrap by `internal/nshost` tests (one supervisor spawns two children that write the same shared file, exit codes propagate). The overlay sharing itself needs an overlay-capable bwrap (can't run nested in the dev sandbox) and is validated on a real host: run a head with a `cow_paths` entry, open a sandboxed bash terminal, `echo aa > <cow_dir>/test.txt` now succeeds and is visible to the agent. `go vet` green.

    ### Revised direction (feedback 2026-06-29): tests are a **merge gate**, not a diff artifact

    The framing above ("mirror artifacts, diff the two refs side-by-side") is the wrong model. The artifacts diff exists because rendered output *is* the product and you want to see what changed. For tests the question is almost never "which cases changed between base and branch" — it's **"is this branch green, and can I merge it?"** Diffing tests is actively worse: it costs a second run against the base, the base is usually already green (so the comparison is mostly noise), flaky cases make the per-case delta jittery, and "passing→failing" is fragile to reorders/renames. So: **drop the side-by-side diff and the repository `.hydra/tests` browser folder.** Surface a single-sided pass/fail verdict for the head's current commit, drilldown-able, and wire it into the merge button.

    What carries over **unchanged** from the design above: the `[[tests]]` config block (`config.TestScript`, same fields/tri-state as `ArtifactScript`), the sandboxed-by-default run with `HYDRA_TEST_OUTPUT/SOURCE/REF`, the JUnit-XML-first + Hydra-JSON parser into `TestReport { total, passed, failed, skipped, durationMs, cases:[…] }`, and **wholesale reuse of the artifacts pipeline** — `internal/artifacts` `Manager` + `slotPool` (`slots.go`) + `genScheduler` + `Subscribe()` live-log/progress, cache keyed by resolved commit SHA (or worktree hash for uncommitted). A test run is just an artifacts generation whose post-step is `parseReports` instead of `scanOutputs`; its `Status` enum (`ready|generating|error`) maps directly to the verdict states below. **Do not fork that machinery** — sibling `internal/tests` package over the shared slot-pool/sandbox/cache helpers, per decision (a) above.

    **Brief for `claude design` (UI/UX + interaction):**

    1. **Verdict states** (richer than running/success/failed — design the badge + colors for all of these):
       - `passing` (green) — ran, 0 failed. Show skip count if any (`✓ 142 · ⊘ 3`).
       - `failing` (red) — ran, ≥1 failed. This is the gate trigger.
       - `running` (blue/spinner) — generation in flight; reuse the artifacts "Generating N/M" progress + elapsed timer.
       - `errored` (amber) — the command itself couldn't produce a report (crashed, timed out, bad config). **Distinct from `failing`** — it means "we don't know", not "tests are red". Retryable via the existing `Invalidate`/refresh.
       - `stale` (gray) — a cached verdict exists but predates the head's latest commit (new commit landed since the run). Offer a one-click re-run.
       - `none` (no chip) — no `[[tests]]` configured, or never run. Must **not** block merge.
       The verdict is a per-commit-SHA cache entry (like artifacts `meta.json`), not an agent operation state — surface it on `AgentResponse` as a small `tests` object (status + counts + duration + the SHA it was computed for), so the sidebar/agent header can show a chip without opening a panel.

    2. **Tests panel / drilldown** — single-sided (no before/after columns). Header summary `✓ 142  ✗ 2  ⊘ 3 · 4.2s`; below it an expandable list of cases, **failing first**, each showing name + failure `message` (and a live log tail while `running`, reusing `ArtifactLogView`). Lives as a tab/section in the diff viewer area (where `ArtifactsPanel` mounts) and/or a chip-click popover from the agent header. Manual refresh button = `Invalidate` + re-`Get`.

    3. **Merge gate (soft, never a hard wall).** When a head's verdict is `failing` (or `errored`), the normal **Merge** action is blocked with an inline reason ("2 tests failing — view results"). The gate is *soft*: a **Force merge** affordance is always present and merges anyway after a confirm that names what's being overridden. `none`/`stale` never block (stale offers "run tests first" but doesn't force it). Model on the API as a `force` boolean on the existing merge endpoint; the handler runs the gate check after the `idle→merging` CAS claim (`handlers.go:1129`) and before `git.Merge` (`handlers.go:1180`), returning a new `409 tests_failing` (with the failing count) unless `force`. "Don't wait" and "override" — the two things conflated in the request — collapse into this one `force` path (force while `running` = don't wait; force while `failing` = override result).

    4. **Merge-when-green (auto-merge queue)** — the ergonomic centerpiece. From a head whose tests are `running` (or that you want to re-test then merge), arm **"Merge when green"**: a persisted intent on the head that fires the merge automatically when the run settles `passing`, and **cancels with a notification** if it settles `failing`/`errored`. Implementation: a nullable `MergeWhenGreen` marker on the `Agent` row (+ who/when), watched by the daemon — hook the artifacts/tests `Subscribe()` `settled` event (the same event that drives the live panel) so no new polling loop is needed; on `settled` for an armed head, run the standard merge path with the gate already satisfied. Arming kicks a fresh run if none is in flight/fresh. **Cancellation triggers:** a new commit on the branch (verdict goes stale → re-run, intent persists across the re-run), the run failing, manual disarm, or the head being killed. Show the armed state on the merge button ("Merge when green ✓ — cancel") and as a sidebar chip.

    5. **Merge button states** to design (one control, context-dependent): `Merge` (verdict passing or no tests) · `Merge ⚠ (tests failing) → Force` (verdict failing) · `Merge when green ▸` split-button (verdict running, or user opts to test-then-merge) · `Merge when green ✓ — cancel` (armed) · disabled-with-spinner during the actual merge CAS.

    _When are tests run?_ Lazily when the Tests panel/chip is opened (like artifacts), and on a merge attempt against a head with no fresh verdict. "Merge when green" implies a run. **Auto-run on every commit** is deliberately out of v1 (cost) — it's the obvious follow-up once the gate proves useful.

    _Optional cheap cross-reference (not the diff, an escape hatch):_ when a branch is `failing`, a reviewer's real question is often "was this already broken on `main`?" Rather than a full per-case diff, offer a single lazy "was base green?" lookup — run/recall the base ref's verdict on demand and show one line ("base: ✓ passing" / "base: ✗ 2 failing — pre-existing"). Decide during design whether even this is worth it for v1; the headline feature is the gate, not the comparison.

    _Net effect on the wiring list above:_ keep the `[[tests]]` config + `TestScript`/`TestReport` schemas + the Settings "Tests" editor section + the simulation fixtures + the generation/cache reuse. **Drop** `TestCaseDelta`, `tests.Compare`, the side-by-side panel, and the `…/repository/tests` endpoints. **Add** the `tests` summary on `AgentResponse`, the single-sided `GET …/agents/{id}/tests` (with `refresh`), the `force` param + `tests_failing` 409 on the merge endpoint, and the `MergeWhenGreen` field + daemon `settled`-hook watcher.

    _Open decisions for `claude design` to call:_ (i) does the gate also block on `errored`, or only on `failing` (lean: block on both, since "unknown" before a merge is itself a reason to pause — but make the force copy distinguish them); (ii) is the base-green cross-reference in v1 or cut; (iii) where the Tests surface primarily lives — a diff-viewer tab vs. a header-chip popover vs. both.

[x] **[Sandbox]** **Run `.hydra/config.toml` commands under `set -eo pipefail` (strict mode) by default.** Every user-declared config command was launched as a bare `bash -c <command>` with no shell flags, so a mid-script failure whose *last* command happened to exit 0 was silently swallowed — masking real failures where exit codes drive behavior: artifacts **cache by outcome** (#38), so a half-broken render cached as a success until the ref changed; services **restart on unexpected exit**, so a failed startup step read as healthy; and a `generate | tee out.png` pipe hid the generator's failure entirely. The four launch sites were `internal/artifacts/artifacts.go` (`[[artifacts]]`), `internal/services/services.go` (`[[services]]`), `internal/heads/heads.go`+`nshost.go` (`pre_exit_script`), and `internal/sandbox/sandbox.go` `withPreSpawn` (`pre_spawn_script`).

    _Done:_ commands now run under `set -eo pipefail` (errexit + pipefail) by default. **`nounset` (`-u`) is deliberately omitted** — config scripts routinely read optional env vars, and aborting on the first unset one would break too many real scripts. A shared `sandbox.StrictShellPreamble`/`StrictScript(cmd)` helper prepends the preamble; `[[artifacts]]`/`[[services]]` gained a `strict` opt-out (`config.ArtifactScript.Strict`/`ServiceScript.Strict` `*bool`, default-on via `IsStrict()`, mirroring `IsEnabled`), threaded through the TOML round-trip (field emitters + renderer doc blocks + the live `.hydra/config.toml`), the API (`strict` on both schemas, regenerated Go stub + TS client), the handler mappings, and a **Strict mode** checkbox in the Settings artifacts + services editors. `pre_spawn_script` and `pre_exit_script` are single inline scripts (no array entry to hang a field on), so they apply strict automatically with `set +e`-as-first-line / `cmd || true` as the documented opt-out — pre_exit notes that teardown wanting best-effort should use it.

    _pre_spawn is interpreter-aware (`set -o pipefail` is a bashism):_ the preamble is applied only when the script's interpreter is bash — no shebang (defaults to `/bin/bash`), an explicit `#!/<…>/bash`, or `#!/<…>/env bash` (new `sandbox.interpIsBash`, which skips `env`'s own flags/`VAR=val` assignments to find the program word). A `#!/bin/zsh` / `#!/bin/sh` / `#!/usr/bin/env python3` script is left untouched. The existing `pre_spawn` EXIT-trap diagnostic (#43) now also fires on an errexit abort, so a failing setup step reads as "your pre_spawn_script failed" rather than a mystery startup death.

    _Also fixed (doc drift the audit surfaced):_ `ArtifactScript.Command` doc + the OpenAPI `command` description said `sh -c`, and `PreSpawnScript` said `/bin/sh`, but all paths actually use `bash -c` (or a shebang-selected interpreter) — corrected to match the code.
